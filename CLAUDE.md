## What StudyMax is (see README.md for full detail)

Upload a transcript → StudyMax tells you what credential (specialization/certificate/minor) you're closest to finishing, the one course that advances the most of it, a term-by-term plan, and it calls your phone about the scholarship deadline closing soonest. Fully working end-to-end only for **Computer Science at University of Saskatchewan** right now; other programs are partially mapped or unmapped.

Matching/planning are deterministic (`src/lib/match.ts`, `src/lib/plan.ts`, `src/lib/credentials.ts`); an OpenAI model (`gpt-5-mini`, called only from `api/_openai.ts`) handles just the parts that need real reasoning (transcript parsing, scholarship "why this fits you" copy, guidance for unmapped schools).

## Current features (what's actually built and demoable today)

- Transcript upload (PDF — DegreeWorks audit or unofficial transcript), parsed by the model into completed vs. in-progress courses.
- Manual course entry: search across the full catalogue by code or title, or browse the Arts & Science course list and tick courses by hand.
- Credential matching: what specialization/certificate/minor you're closest to finishing, and the single highest-overlap course you haven't taken yet.
- Term-by-term plan, drawn as a roadmap (see Plan roadmap below), with prerequisite chains expanded automatically (including prereqs the specialization page itself never lists). It starts in a term the student picks and counts in-progress courses as passed by then; onboarding seeds it with the chosen concentrations first, then the minor's requirement lists.
- Certificates/minors detector — surfaces credentials a student is partway through without knowing it.
- Scholarships/awards ranked by deadline, with AI-generated "why this fits you" copy.
- Class Tracker tab (USask only): look up a course's sections and watch live seat counts from USask's own class search (`api/classes.ts`, `api/_banner.ts`), with a badge when a watched seat opens.
- Outbound phone call (via Bland) about the award closing soonest — one-way, says its piece, hangs up.
- "Load a sample student" — a bulletproof canned path for demoing without a real transcript.
- Full end-to-end support for Computer Science at University of Saskatchewan; partial data (plan-only, no credential detection) for Applied Mathematics, Physics, and Applied Computing, and degree-requirement plans for Biology, Psychology, Engineering, Nursing, Agriculture, Commerce, Kinesiology and Education; every other Arts & Science subject reaches only the scholarship side.

## Code structure: component-first, no more god pages

The app is a screen flow, not one page. `src/App.tsx` owns the state in one `useStudyMax()` hook and hands it to screens through `ModelContext` (`src/model.ts`, read with `useModel()`); it renders exactly one screen at a time with a directional transition. Keep it that way:

- Screens live in `src/screens/` (Welcome, the onboarding steps, Courses, Reading, Reveal, Results with its Overview/Plan/Awards tabs, Call, AccountSheet). Shared UI lives in `src/ui/`: `primitives.tsx` (Button, Group, Row, Appear, Ring, Chip…), `chrome.tsx` (TopBar, ScreenBody, ScreenTitle, ActionBar), `Sheet.tsx`, `motion.ts`, `Icon.tsx`. Build new UI from those, not from new CSS.
- The design system is `tokens.css` + `src/App.css`: Old Lace #FFF8EB page, ink #12262B, Cherry Rose #982649 as the single accent, Rosy Taupe #C38D94 as its tonal partner, no pure white/black. No component invents a colour, size or duration; it asks the tokens.
- A new piece of UI gets its own file with clearly typed props (or reads the model), not another inline block in `App.tsx`. Logic that isn't UI (matching, planning, credentials) stays in `src/lib/`.
- `src/platform.ts` wraps everything native (haptics, Android back button, splash, keyboard, the API base URL); `src/auth.ts` is the one sign-in module for native and web.

## OpenAI helper

Every AI route (`api/parse-transcript.ts`, `api/why-you.ts`, `api/scholarship-guidance.ts`) calls `respond()` in `api/_openai.ts` and answers failures with `sendFailure()`. Don't add a route that calls OpenAI directly.

- `gpt-5-mini` on Chat Completions with `reasoning_effort: 'minimal'` and `store: false`. Uncapped, gpt-5-mini can spend its whole token budget on hidden reasoning and return empty text. Minimal against low, and Chat Completions against Responses, were measured on a synthetic transcript: minimal was 2–5x faster and always correct.
- The key only travels in the Authorization header. OpenAI's error text never leaves the server: its invalid-key error quotes part of the key and its rate-limit error names the org. The browser gets `{ error, status }`; the log gets the status and OpenAI's error code.
- `api/features.ts` reports `ai`/`call` from whether `OPENAI_API_KEY`/`BLAND_API_KEY` are set, and the app hides what's missing.

## The degree planner: real rules from real data

Every CS plan is the whole B.Sc.: the Four-year by default (120 cu, 66 at the 200 level or higher), or the Honours (120/66) or Three-year (90/42) the student picks, built only from committed static data; nothing calls Banner or the catalogue at runtime.

- **Data and how to regenerate it:** `src/data/prereqs.ts` and `src/data/activeCourses.ts` come from the public catalogue JSON API (`https://catalogue.usask.ca/api?subj_code=X`, `/api/course_titles`) via `scripts/scrape-catalogue.ts`: prerequisites (`requires`, earlier term), `concurrent` (same term allowed), `creditRequires`, `antirequisites`, `offered` (2026-27). `src/data/creditPrereqs.ts` pins the credit-count prerequisites the demo depends on. `src/data/offerings.ts` (Ayo's `scripts/scrape-offerings.ts`, Banner 2025-27) says which terms a course actually ran; it beats the catalogue's `offered`. `src/data/breadth.ts` (`scripts/build-breadth.ts` from Banner section-attribute dumps, Fall 2026) gives each course's program types (HUM, SOCS, FNAR, ...) so senior breadth counts.
- **Degree model in credit units:** `src/data/degrees/types.ts` (`Degree`, `DegreeGroup` with `needCu`, `oneOf`/`allOf`, `matches` wildcards, area caps, `typeMin`, advising `year`/`yearCu`, `flexible`), the CS data in `src/data/degrees/computerScience.ts` (Four-year, Honours and Three-year, all in `Program.degrees`; the student picks one under Degree in the Plan settings, `degreeVariant` in the saved state, device-only, default Four-year, and App.tsx's `activeDegree` feeds matching, the plan and the tree), and the audit `src/lib/degree.ts` (`auditDegree`: each course counts once, caps, the college's maximum junior credit by subject from `src/data/degrees/juniorCaps.ts` (CMPT 12, ENG 6 plus ENG 120, ...; past it, 100-level credit counts toward nothing, so the planner adds electives), and junior credit up to total minus senior). `Program.degree` is this model (the Four-year for CS).
- **Course data the planner reads:** one `Catalog` (`src/lib/catalog.ts` `defaultCatalog()`, type in `src/lib/planner/types.ts`): Banner's seasons (`offerings.ts`, then `SEASON_OVERRIDES` for sections the scrape missed such as CMPT 400/405/407, then the per-term history in `src/data/bannerHistory.ts` from `scripts/build-banner-history.ts`) beat the catalogue's `offered`; an offering `confidence` (published, annual-pattern, alternating-pattern, catalogue-only, unknown) and `atRisk` (no section in 10 terms: CMPT 440, MATH 314/436/438) from `src/data/offeringConfidence.ts`; `fullYear` (the catalogue's "Term 1 and 2", a seat in a Fall AND the next Winter); hand-fixed prerequisites in `src/data/prereqOverrides.ts` (exact CNF for EE 216, MATH 134/339/352/361/362/439, CHEM 115/250, STAT 342/349/443, POLS 236; CMPT 489 without CMPT 498) that win over the scraper; `minGrade` as data only. `scripts/check-offerings.ts` fails when a required course stopped running and its specialization isn't marked `atRisk` (Programming Languages, Cybersecurity, Computer Systems are).
- **The planner (`src/lib/planner/`, pure, no AI, no React, no data imports in the core):** `buildStudentPlanResult(targets, specs, completed, inProgress, load, start, options)` in `src/lib/plan.ts` returns `{ terms, graduation, optimality: 'proven' | 'best-found', binding, bindingKind, diagnostics }`; `buildStudentPlan(...)` is its adapter and returns `terms` (PlannedTerm[], unchanged shape, so the tree, roadmap, What if, Share, Register and Max are untouched). Pipeline: `applyOverrides` (`src/lib/overrides.ts`) → match → selection (the ranker's L2-best pick, then `select.ts` tries like-for-like alternatives best-first when they could graduate earlier, at most 8 selections) → `model.ts` (items, terms, diagnostics) → `schedule.ts` `scheduleCore` (lower bound with the binding constraint named; for H = LB, LB+1, …: deadlines back from H, list scheduling in several deterministic orders, then an exact DFS with a node budget) → `explain.ts` (binding text, `diffPlans`). `planner/index.ts` exports `planExact` and `replan(prev, ...args) → { result, diff }`. There is no relaxation anywhere: RELAX_AFTER, MAX_TERMS and the catch-all term are gone.
- **The objective (exactly one plan per input; `src/lib/planner/types.ts`):** L0 hard rules, never relaxed: the course runs that season and the term isn't blocked; prerequisites passed in an EARLIER term (a `concurrent` group may share it); credit rules, Honours standing, 300-level from 30 cu and 400-level from 60 cu; planned courses per term <= max(0, load - booked) with load 1-5 Fall/Winter and 0-2 Spring/Summer (0 = no Spring/Summer term); <=15 cu per Fall/Winter term; <=3 senior CMPT a term and none in Spring/Summer; one course per requirement slot; antirequisites excluded; booked courses fixed; a full-year course takes a seat in its Fall and the next Winter; the internship year empty. Then L1 earliest graduation; L2 selection fidelity (the degree's `prefer`/recommended course unless it costs a term); L3 fewest Spring/Summer courses; L4 terms filled to the load, advising years respected; L5 a canonical tie-break on (group, code) with plain `<`, never localeCompare. L1 is proven (the result equals the lower bound, or the exact search proved every earlier term infeasible) for the selected courses; L3-L5 are a deterministic procedure. Budgets count nodes, never milliseconds, so iOS, Android, Node and Vercel agree.
- **Settled rules:** an elective slot counts 3 cu toward the level gates once its term ends (credit-count rules count named courses only, the stricter reading); booked courses above the load are shown (BOOKED_OVER_LOAD), never grown; without a degree (programs other than CS, What if) each earlier Fall/Winter term is assumed full of other courses for the level gates.
- **Diagnostics:** errors leave a course OUT of the plan instead of bending a rule: NO_OFFERING, PREREQ_UNREACHABLE (and its dependants), CYCLE, STANDING (CMPT 400 on a non-Honours degree), SUMMER_ONLY (with Spring/Summer 0), HORIZON; warnings: UNKNOWN_OFFERING (placed in Fall/Winter only, "offering unconfirmed"), AT_RISK, BOOKED_OVER_LOAD, EMPTY_SEAT (with the reason); override notes RETAKE, UNBOOKED, BLOCKED, OVERRIDE_INVALID. `binding` says what sets graduation ("Graduation set by MATH 116 → STAT 241 → STAT 242 → CMPT 317 → CMPT 423 → CMPT 489", "your load of 5 a term").
- **Overrides ("life happened", `src/lib/overrides.ts`, device-only in SavedState):** `CourseOverride { code, term, kind: 'failed' | 'withdrew' | 'not-offered' | 'later' }`. failed/withdrew (current or past term) take the course out of completed/in progress/booked; it comes back as a retake if still needed, and a booked or in-progress course that depended only on it is un-booked, transitively, with "You're registered for CMPT 434 in Winter 2027 but it needs CMPT 332; the plan moves it. Check with the department." not-offered/later (current or future term) block that one term and move the course to the next term that really runs it, or an alternative takes over. Invalid ones are dropped with a note; canonical order is term, kind, code. Replanning is the same pure function on the updated inputs. UI: "Something changed?" in `TreeDetail` and the roadmap's `CourseDetail`, Failed / Withdrew / Cancelled this term on Courses' in-progress rows, and the "What changed" sheet (`src/ui/WhatChanged.tsx`) with each move's cause, the graduation change and Undo.
- **Loads, one source of truth:** `src/lib/planner/loads.ts` (`FW_LOADS` 1-5, `SUMMER_LOADS` 0-2, `clampLoad`, `clampSummer` (a stored 3 becomes 2), `summerLoadOf`), read by onboarding, Plan settings (through `cloudSession.ts`'s maxima), What if, the cloud session and Max. The `springSummer` boolean survives only at the edges.
- **Max:** `planningAdapter.regenerate()` plans the way the app does (degree, credentials, minor, the student's loads, booked courses); `validate()` warns on AT_RISK courses; `PLANNER_VERSION` is `lib/planner@exact-v4` and the inputs hash covers every planner input.
- **The suite (run all of it after any planner or data change; each is `node --experimental-strip-types --experimental-loader ./scripts/_resolve-ts-loader.mjs scripts/<name>.ts`):** `check-degree.ts` (I1-I10 against the published rules in `scripts/_degree-rules.ts`, now at loads 1-5 × Spring/Summer 0-2; I1 booked-aware; I7 and I9 at load 5, I7 counting a full-year course's two seats); `check-plan-validator.ts` (an independent V1-V12 validator, `scripts/_plan-validate.ts`, that imports no planner code, over the 1,620-case matrix in `scripts/_plan-matrix.ts` and 4,800 override plans); `check-plan-oracle.ts` (an exact BFS on 2,000 seeded random instances plus 20 real CS subsets: the engine's graduation must equal the optimum, and `--dump=random#N` prints an instance); `check-plan-properties.ts` (determinism under repeats and shuffles, monotonicity in load, Spring/Summer, failures and completed courses, booked courses never move, replanning after doing the first term never moves graduation, never later than `scripts/plan-baseline.json` (the old greedy planner's graduation, allowing one term per full-year seat it ignored), and runtime p50/p95/max); `check-overrides.ts`; `check-offerings.ts`; plus `check-plan.ts`, `check-skill-tree.ts`, `check-planning-adapter.ts`. Exact prefix/replan plan identity is reported, not gated: the planner re-optimises from its inputs alone, so it may re-pick among equally early plans for future, unregistered terms.
- **Not modelled yet:** offerings per academic year (alternating-year courses look annual unless the confidence flag says otherwise); Spring and Summer as separate sessions (one Spring/Summer season, capped 0-2 across May-August); grade minimums and the college repeat rules (data only); the transcript parser still drops failed and withdrawn attempts (mark them with an override); a whole-degree model for programs other than CS (their plans cover the major's requirements and say so); the all-four rule for BIOL 102.1/CHEM 142.1/GEOL 102.1/PHYS 152.1, the Honours Software Engineering option, the policy that specializations are Four-year and Honours only (a Three-year plan still plans one), and the rules of programs other than CS (their plans cover the major and say so).

## Plan roadmap

## Academic Skill Tree

The Plan's default view (a "Tree · Roadmap" switch at the top of the Plan tab and the desktop Plan page, remembered in localStorage) draws the degree as a tree that grows up: roots at the bottom, Year 1 above them, the years rising to a canopy of the credentials being worked toward. It opens scrolled to the roots and you scroll UP to grow. It's a new view of data the app already computes, never new scheduling.

- **Files:** `src/lib/skillTree.ts` (pure layout: `layoutSkillTree()`, `treeTargets()`, `pathThrough()`), `src/skilltree/` (`SkillTree.tsx` the tree and its interaction, `TreeDetail.tsx` the sheet or docked panel, `planView.ts` the view switch and the model wiring, `skilltree.css`), and `scripts/check-skill-tree.ts`.
- **Placement:** every card sits in its own term: registered courses in the term they're registered for ("Registered · Winter 2027"), planned ones in the plan's term, completed ones in the term the transcript dated (`completedTerms`) or, undated, in the year of their course level (approximate, and the sheet says so). No Fall or Winter lane holds more than the student's load, Spring/Summer has its own capped lane, and the current year comes from credit units done. Above the canopy a degree readout ("84 of 120 cu", C1-C5 done or left, `src/skilltree/DegreeReadout.tsx`, fed by `src/lib/degreeProgress.ts`), and milestones on the trunk (CS major admission after Year 1, the Honours application at 60 cu). Undated completed courses within a year: within a year, a course with a prerequisite in the same year goes Winter (right), one that unlocks a course in the same year goes Fall (left), the rest alternate by code. A prerequisite the catalogue lets you take concurrently doesn't sequence (CMPT 141 stays in Fall with MATH 110). In-progress courses take the current term; planned ones the plan's own term, relative to the current year (roughly ten courses a year, never earlier than the highest completed level). Prerequisites always sit below what they unlock; electives (a planned pick for a "1 of N" slot) take the outer edge. An internship year (asked in Goals, or on the review when a path skips Goals; changeable on the Plan tab) is a whole academic year the plan leaves empty (`away` in `PlanOptions`); its band gets a dashed frame and, when empty, an "Internship year" card on the trunk. `studentYear()` in `skillTree.ts` is the one definition of which year the student is in, shared by the tree and the plan's internship year. On a transcript that dates nearly every course, the few undated ones are transfer credit: they sit in their level's year (Year 1 for CMPT 141/145 from another school), over the load if need be, and never add a year.
- **Look:** on the app's own page, rose-led. A tapered Rosy Taupe trunk and soft roots; app-style cards on short twigs (one per side on a phone so titles fit, two on desktop). Done is a Cherry Rose card, Taking now a breathing rose outline, Take next the single haloed card with a Next tag (the app's top-overlap course when it's in the plan), Planned a taupe outline, Elective dashed, Locked muted with "Needs X first". The hero credential is rose; up to three others get a quiet teal, plum or sand ring and branch (`--tree-cred-*`, with dark variants). Prerequisite links are drawn only for the course you select, and only its own (what it needs, what it unlocks, matching its detail panel): each ends in an arrowhead at the course it unlocks, a glowing signal runs along it in that direction, and the cards are masked out of the link layer so a line passes under a course, never across its text. On a phone a tap shows a slim peek over the tab bar (`src/skilltree/TreePeek.tsx`: Needs, Unlocks, Details for the full sheet) so the arrows stay visible, and the key folds behind a Key button so only the chips row stays pinned. The tree's own scroll box shows no scrollbar. No circuit-board look, no technical words: Ibraheem rejected that version.
- **Motion and access:** the trunk grows up through a mask (stroke-dashoffset), each year settles in as it scrolls into view, the leaves bloom; everything is static under reduced motion. Every card is a labelled button; arrows move between cards, Home and End jump to the roots and the canopy.

## Database

Schema lives in `prisma/schema.prisma`, migrated onto the team's shared remote Supabase Postgres. The app syncs a signed-in student's session through `api/session.ts` (GET/PUT, Firebase ID token verified in `api/_firebaseAuth.ts`, Prisma client in `api/_db.ts`); it stays local-first, with localStorage as what it runs from and the DB filling in a session on a phone that has none. Identity is the Firebase uid in `UserInfo.authUid`; guests never touch the DB — see `docs/databaseSpec.md` for what each table is for and what's deliberately not in the DB (the course catalogue/programs/scholarships stay static files).

- **Use `prisma migrate deploy`, never `prisma migrate dev`.** There's no local/shadow database here — only the one shared remote instance — and `migrate dev` provisions a shadow DB to diff against, which isn't the right model for four people hitting the same remote schema. Write migration SQL with `prisma migrate diff` (or by hand for something simple like a rename), then apply it with `npm run db:migrate` (wraps `prisma migrate deploy`).
- Prisma's CLI doesn't read `.env.local` — `db:migrate`/`db:studio` are wrapped in `dotenv-cli` for this reason. Don't add a plain `.env` with the same values instead.
- `Institution`/`Major` are seeded reference tables (`npm run db:seed`), not something to hand-edit rows into for testing — add to the JSON files in `scripts/` and reseed if a row is missing.

## The `.js`-extension convention, and where it now reaches

`api/*.ts` files have always used `.js` extensions on relative imports even though the source is
`.ts` (NodeNext module resolution — Vercel's Node builder transpiles each `.ts` file to a same-named
`.js` file without rewriting import specifiers, so a `.ts`-suffixed import 404s at runtime; Vite
doesn't have this problem, since it fully bundles). Since BayMax (Max), `api/session.ts` and
`api/max/_scenarios.ts` genuinely execute (not just type-import) `src/lib/plan.ts` and the whole
`src/data/programs/*` graph server-side, so those files — and everything they import — now use `.js`
extensions too (see `git log` for the exact file list; anything under `src/lib/max/`, `src/lib/plan.ts`,
`src/lib/match.ts`, and `src/data/programs/**`/`specializations.ts`/`prereqs.ts`/`offerings.ts`/
`transcript.ts`/`courseTitles.ts`/`courses.ts`). This is safe for Vite (which resolves `.js` specifiers
to a sibling `.ts` file fine) but breaks plain Node, which doesn't do that fallback — so any script
that imports one of those files needs `scripts/_resolve-ts-loader.mjs`:
```
node --experimental-strip-types --experimental-loader ./scripts/_resolve-ts-loader.mjs scripts/whatever.ts
```
Check each script's own header comment for its exact invocation — the affected ones already have it.
If you add a new program file or touch this graph, keep using `.js` extensions in its own imports,
matching its siblings, not the plain `.ts` most of the rest of `src/` still uses.

## Why we're not done: the three gaps to a winning submission

Ranked by what actually swings judges, in order of what to protect first:

1. **Demo polish & story.** The pitch and the live-demo path have to be flawless — no rough loading/error/empty states, no dead ends judges can wander into. The "reveal" moment (finding what you're close to) and the phone call at the end are the emotional payoff of the pitch; they need to land every single time we run the demo, including offline/no-real-transcript scenarios. **The sample data path ("Load a sample student" on the Courses screen) is the demo's safety net — it must never break.**
2. **Breadth beyond CS/USask.** Right now the "wow, it actually works" moment only exists for one program at one school. Per the README, adding a program is a **data task, not an engineering one**: one file in `src/data/programs/`, registered in `index.ts`, and matching/planning/credentials pick it up automatically. This is the highest-leverage way to make the product look bigger than it is — but only add programs if the data is trustworthy enough not to visibly break the demo (see `check-course-codes.ts`, `check-schools.ts`).
3. **A standout "wow" feature.** We need at least one moment in the demo that judges haven't seen in another submission. Not yet decided what this is — flag ideas to the team rather than unilaterally committing to a large new feature.

## Mobile build

The same Vite app ships as iOS and Android apps through Capacitor 8 (`capacitor.config.ts`, `ios/`, `android/`; app id `ai.calendue.studymax`). Native Apple and Google sign-in go through `@capacitor-firebase/authentication` against Firebase project `studymax-3a090`; the web uses the Firebase JS SDK only when the four `VITE_FIREBASE_*` vars are set, otherwise it starts as a guest. The native apps call the API at `https://study-max-theta.vercel.app` (`src/platform.ts`). Features that need `OPENAI_API_KEY` or `BLAND_API_KEY` are gated by `/api/features` (`src/features.ts`), so they stay hidden until those keys are in Vercel.

- `npm run build` then `npx cap sync` copies `dist/` into both native projects; open `ios/App/App.xcodeproj` or `android/` to run on a simulator/emulator.
- `npm run build:ios` builds the signed ad hoc IPA into `release/`; `npm run build:android` builds the signed APK. `npm run cap:assets` regenerates icons and splash.
- Never committed (gitignored): `ios/App/App/GoogleService-Info.plist`, `android/app/google-services.json`, `android/keystore.properties` and keystores, `release/`, `.env.local`. Get them from a teammate or the Firebase console.
- Native API calls go to the deployed Vercel site (`API_BASE` in `src/platform.ts`), so `api/` changes must be deployed before the app sees them.

## How to work during this sprint

- **Speed over ceremony.** This is a hackathon, not production software — favor small, shippable increments over the "right" long-term abstraction. It's fine to hardcode something for a specific demo path if it removes real risk.
- **Don't break the deployed demo.** The app is live on Vercel and gets demoed directly from it. Treat `main` as "must always be demoable" — prefer smaller, verifiable commits over big risky refactors close to demo time, and call out anything that could jeopardize the CS/USask happy path *before* touching it.
- **Keep the cheap safety nets, skip the expensive ones.** The `scripts/check-*.ts` asserts and `npm run lint && npm run build` are fast and catch exactly the kind of silent data breakage (a course code the catalogue dropped, a scholarship link that 404s) that would be embarrassing live — keep running them before calling something done. Don't add new test infrastructure or heavy process during the sprint.
- **Four people editing the same small codebase.** Keep diffs scoped and legible so teammates can tell what changed and why at a glance; avoid unrelated drive-by refactors while everyone's moving fast in parallel.
- **When in doubt, ask.** With this little runway, a wrong guess that has to be unwound costs more than a 10-second clarifying question — especially for anything that touches the demo path or judging story.
- **Don't use the claude-in-chrome tool in this project.** Verify UI changes another way (build, lint, `npm run dev` + reading the code, or ask the user to check).
